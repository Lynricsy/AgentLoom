10 · 实现 A

契约层：一份 schema 怎么走到三端

这里其实是两条并行的链，讲的时候不能混为一谈 —— REST 走 OpenAPI 生成，Socket 走 fixture 对锁。

链 A · REST：Zod 定义 → 生成类型

01Zod schema含 transform 归一 snake/camel、superRefine 补校验
02createZodDto包成类，同时喂运行时校验与 Swagger
03openapi:exportnest build 后启动 app 导出 spec 文件
04生成器openapi-generator 出 models.ts
05Studioimport type，改字段前端 tsc 就红

controller 里的真实写法

async create(
  @Body(new ZodValidationPipe(CreateAgentDefinitionSchema))
  dto: CreateAgentDefinitionDto, // 仅作类型，type-only import
) { ... }

值得注意：DTO 类只提供 TS 类型与 Swagger 元数据，运行时校验靠显式传进管道的那份 schema。另有一个同名的全局管道兜底，靠检测形参上的 .schema 静态属性工作。

校验失败长什么样

不是默认的 400，而是 422 + application/problem+json；errors 数组每条是「字段路径 + 消息」，字段路径由 Zod issue 的 path 用点连接而成。

链 B · Socket wire：fixture 双向对锁

契约包里放一批服务端真实输出形状的 JSON。契约侧断言「目录里的文件集合、映射表的键、事件名数组」三者两两全等；服务端侧用 同一批文件 比对自己真实发出的信封。服务端偷偷改 wire 格式，两边同时变红。

三个反直觉的点（讲出来很加分） 一、生成产物不是纯 interface —— 枚举以 as const 对象形式保留，所以前端能当运行时值用。二、「禁止手改」的标记不在文件头，在包的 README 与 AGENTS.md 里。三、运行时 /openapi.json 端点与导出的 spec 文件不是同一份文档 —— 导出脚本额外做了通配路径参数、元组降级、标量联合三步归一，运行时端点不做。
11 · 实现 B

沙箱边界：四道各自独立的闸

文件、解包、网络、凭据四处各有独立实现，共同原则只有一条：默认拒绝，校验后放行。文件校验全部发生在沙箱内的 Go 进程里，不在服务端。

文件侧：三个函数各管一类操作

函数判定步骤
读/通用路径拒空串与 NUL 字节 → 规范化 → 必须绝对路径且在固定根内 → 解开软链接 → 解开后再判一次根边界 → 需目录时确认确实是目录
写文件同上前两步 → 不许把根本身当文件写 → 用不跟随软链接的方式取状态：已存在则必须是常规文件（拒目录、管道、设备节点）并解链后再判根；不存在则解析父目录、确认父目录是目录且在根内
解 tar 条目拒绝绝对路径与 NUL → 拼接后规范化 → 必须仍以目标目录加分隔符为前缀。两个调用点：条目名与硬链接名

固定根只有两个，前缀匹配带路径分隔符 —— 否则 /workspace-evil 这类前缀伪装会通过。

网络侧：网卡入口五条规则，最后一条兜底

// 入口方向，优先级从小到大
10  IP   src_ip==分配IP 且 src_mac==分配MAC → pass
11  ARP  src_mac==分配MAC 且 arp_sip==分配IP → pass
12  IPv6 → drop
20  matchall → drop

在 CNI 建好网络之后下发；任一条失败，两层 defer 分别回滚 CNI 与网络命名空间。另有一套防火墙规则以整表单事务下发，其中包含「沙箱之间互访直接丢弃」与「访问私网段直接丢弃」两条。

凭据侧：两段都验对方

服务端到虚拟机管理器是双向 TLS：服务端加载 ca/cert/key，管理器侧要求并验证客户端证书且强制 TLS 1.3。管理器转发到沙箱内时，先剥掉入站的 Authorization 头再注入沙箱自己的令牌 —— 外部无法把凭据透传进去。沙箱内令牌用恒定时间比较。

12 · 实现 C

多租户：真正生效的是哪一条链

两条消费链，别混讲 租户中间件解出的 tenantId 只做 base64url 解码、不验签，写在原生 request 上，之后被限流守卫拷到框架 request 上。它有两类消费者：限流与配额计费，以及一部分 controller —— 有的优先读它、回退到验签值，有的只读它。而下面这条数据隔离链只读验签后的 request.user.tenantId。所以「数据隔离不读它」是对的，「唯一消费者是限流」是错的。

真正的隔离链

01AuthGuard 验签验 JWT 签名与 audience，把可信身份写入 request.user
02TenantGuard租户准入，随后 RolesGuard 判角色
03事务拦截器读 request.user 的 tenantId，开事务并设上下文
04表级策略68 张表的行级安全策略强制过滤

拦截器在 guards 之后执行，这个顺序不是偶然：可信身份必须先建立，才能拿去设置数据库租户上下文。否则未验签的 claim 会直接影响行级安全的判定结果。API Key 分支不验 JWT，走独立的令牌校验，再把 tenantId 补到 request 上。至于那些直读未验签值的 controller，当前不构成越权 —— 请求必须先通过认证守卫，token 本身已被验过，两个值来自同一份 payload；但这份安全性由链路顺序保证，不是自证的：某天给这些路由挂上跳过认证的标记，它立刻变成越权读。

事务里下发的两句

SET LOCAL ROLE authenticated;
SELECT set_config('app.current_tenant', $1, true);

第三个参数为真表示只在本事务内有效，事务结束自动失效，不会泄漏到连接池里的下一个请求。表上的策略条件是 tenant_id = get_tenant_id()，而那个函数读的就是上面这个配置键。事务对象经异步上下文下发给所有数据访问代码。

只追加的表是怎么做的

审计表没有用触发器：只建 SELECT 与 INSERT 两条策略、并且只授予 SELECT 与 INSERT 权限 —— 策略层与权限层双重保证 UPDATE / DELETE 无从下手。

怎么验证隔离真的生效

集成测试起一个真实数据库容器，逐条回放全部迁移 SQL，然后在带/不带租户上下文两种情形下查询，断言跨租户结果为空数组或直接抛权限错误。

但这条线整体不是闭环 —— 一个未认证的放大面 限流守卫排在认证守卫之前，而它接受未验签解码出来的 tenantId，并用它查该租户的治理状态、按日配额键无条件递增计数器。也就是说：伪造一个签名无效、payload 里填受害者 tenantId 的 token，反复打任意受限流端点，每次都会在最终 401 之前先把受害者的日配额加一；分钟级限流也按同一个未验签值分桶。不泄漏数据，但能把指定租户的配额刷干。修法是配额计费改到验签之后、或对未验签身份只做 IP 维度计数，并补回归测试。
