# Webhook 触发

Webhook 触发器让外部系统通过 HTTP 请求来启动你的工作流。AgentLoom 会为每个 Webhook 触发器生成一个唯一的 URL，外部系统只需向该 URL 发送 HTTP 请求即可触发工作流执行。

## 创建 Webhook 触发器

### 第一步：进入触发器管理

> 界面提示：在工作流编辑页面中，找到触发器管理区域，点击「创建触发器」按钮。

### 第二步：选择触发器类型

在触发器类型选择中，选择「Webhook 触发」。

### 第三步：配置触发参数

填写以下信息：

- **名称**：为触发器设置一个描述性的名称，例如「GitHub Push 回调」
- **描述**（可选）：说明触发器的用途和触发来源
- **认证模式**：选择请求验证方式
  - **简单模式（Simple）**：使用 Token 进行基本验证
  - **签名模式（Signed）**：使用 HMAC 签名进行更安全的验证
- **IP 白名单**（可选）：限制只接受来自指定 IP 地址的请求

### 第四步：确认创建

点击确认按钮后，系统会自动生成以下信息：

- **Webhook URL**：外部系统需要调用的 URL 地址
- **Token**：用于请求验证的令牌
- **Secret**：用于签名验证的密钥（仅创建时显示一次）

> 界面提示：创建成功后，请务必保存好显示的 Token 和 Secret 信息。Secret 仅在创建时显示一次，之后无法再次查看。

## 发送请求格式

外部系统向 Webhook URL 发送 HTTP 请求时，需要遵循以下格式：

### HTTP 方法

使用 `POST` 方法发送请求。

### 请求头

根据你选择的认证模式，需要在请求头中包含相应的验证信息：

**简单模式**：在请求中携带 Token 参数进行验证。

**签名模式**：在请求中包含使用 Secret 生成的 HMAC-SHA256 签名。

### 请求体

请求体中可以包含 JSON 格式的数据，这些数据会作为工作流的输入参数传递。

```json
{
  "message": "新的代码提交",
  "repository": "my-project",
  "branch": "main"
}
```

## 签名验证配置

签名验证（Signed 模式）是比简单 Token 验证更安全的方式。它通过对请求体进行 HMAC-SHA256 签名来确保请求的完整性和来源可信。

### 签名验证的原理

1. 外部系统在发送请求时，使用 Secret 对请求体计算 HMAC-SHA256 签名
2. 将签名值放在请求头中一起发送
3. AgentLoom 接收到请求后，用同样的 Secret 重新计算签名
4. 对比两个签名值，一致则验证通过

### 签名验证的好处

- **防篡改**：确保请求内容在传输过程中没有被修改
- **防伪造**：只有知道 Secret 的系统才能生成正确的签名
- **时序安全**：使用恒定时间比较防止时序攻击

### 签名失败的处理

当签名验证失败时，AgentLoom 会：

- 拒绝触发工作流
- 在触发器的执行历史中记录一条状态为「签名失败（Signature Failed）」的记录
- 不向外部系统透露具体的验证失败原因（安全考虑）

你可以通过查看触发器的执行历史来排查签名失败的情况。

## IP 白名单

为了进一步限制谁可以触发工作流，你可以配置 IP 白名单。只有来自白名单中 IP 地址的请求才会被接受。

- 支持 IPv4 和 IPv6 地址
- 可以配置多个 IP 地址
- 如果不配置白名单，则接受来自任何 IP 的请求

**建议**：如果你的 Webhook 只需要接收来自特定服务器（如 CI/CD 服务器）的请求，配置 IP 白名单可以显著提高安全性。

## 安全建议

### 保护 Secret 信息

- Webhook 的 Secret 仅在创建时显示一次，请立即保存到安全的位置
- 不要在公开的代码仓库或文档中暴露 Secret
- 如果怀疑 Secret 已泄露，应立即删除旧的触发器并创建新的

### 优先使用签名模式

- 简单模式适合快速测试，但在生产环境中建议使用签名模式
- 签名模式可以同时验证请求的来源和完整性

### 配合 IP 白名单使用

- 在条件允许的情况下，同时配置签名验证和 IP 白名单
- 两层保护可以大幅降低未授权触发的风险

### 使用 HTTPS

- 确保调用 Webhook URL 时使用 HTTPS 协议
- HTTPS 可以防止请求内容在传输过程中被窃听

## 与第三方服务集成

许多第三方服务都支持配置 Webhook 回调，以下是常见的集成场景：

### CI/CD 系统

在你的 CI/CD pipeline 的最后一步，添加一个 HTTP 请求步骤，向 AgentLoom 的 Webhook URL 发送通知。这样每次构建完成后都可以自动触发相应的工作流。

### 表单服务

很多在线表单服务（如 Google Forms、Typeform）支持在收到新提交后触发 Webhook。配置后，每当有人提交表单，对应的工作流就会自动启动。

### 监控告警

将监控系统（如 Grafana、Datadog）的告警回调指向 Webhook URL，当触发告警时自动执行工作流进行问题处理。

## 查看执行历史

Webhook 触发器的执行历史会记录每次收到请求后的处理结果：

| 状态 | 说明 |
|------|------|
| 成功 | 请求验证通过，工作流已启动 |
| 失败 | 请求验证通过但触发执行时出错 |
| 跳过 | 请求有效但工作流不满足执行条件 |
| 签名失败 | 请求的签名验证未通过 |

## 常见问题

### 外部系统发送请求后工作流没有执行

检查以下几点：
1. 触发器是否处于启用状态
2. 请求方法是否为 POST
3. Token 或签名是否正确
4. 是否配置了 IP 白名单且请求来源不在白名单中
5. 工作流是否已发布

### 执行历史显示"签名失败"

检查以下几点：
1. 确认 Secret 是否正确
2. 确认签名算法是否为 HMAC-SHA256
3. 确认签名是基于请求体原始内容计算的，不是编码后的内容
