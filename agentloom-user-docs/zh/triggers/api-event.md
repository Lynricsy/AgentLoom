# API 事件触发

API 事件触发器（API Event Trigger）让你的工作流能够响应通过 AgentLoom API 入口发送的外部事件。它特别适合构建事件驱动的自动化体系，支持精确的事件来源识别和类型匹配。

## 基本概念

### 什么是 API 事件

API 事件是外部系统通过 AgentLoom 的统一事件入口（`POST /api/v1/api-events`）发送的结构化事件数据。每个事件包含以下核心信息：

- **事件来源（Event Source）**：标识事件是由哪个系统或平台发出的，例如 `github`、`generic`
- **事件类型（Event Type）**：描述事件的具体类型，例如 `push`、`pull_request`、`issue`
- **事件载荷（Payload）**：事件携带的详细数据

### 事件匹配机制

当 AgentLoom 收到一个 API 事件时，系统会：

1. 根据事件来源找到对应的适配器进行验证
2. 遍历所有已启用的 API 事件触发器
3. 将事件与每个触发器的配置条件进行匹配
4. 对于匹配成功的触发器，启动对应的工作流执行

一个事件可以同时匹配多个触发器，触发多个工作流执行。

## 事件源适配器

AgentLoom 通过事件源适配器（Event Source Adapter）来处理不同来源的事件。每个适配器负责特定来源的事件验证和匹配逻辑。

### GitHub Webhook 适配器

专门处理来自 GitHub 的 Webhook 事件，提供完整的安全验证。

**验证机制**：
- 检查请求中是否包含 `X-Hub-Signature-256` 请求头
- 使用配置的 Secret 和请求体内容计算 HMAC-SHA256 签名
- 对比签名值，使用恒定时间比较防止时序攻击
- 任何验证步骤失败都会拒绝该事件

**事件匹配**：
- 根据触发器配置的事件类型（如 `push`、`pull_request`）与实际事件的类型进行匹配
- 匹配时忽略大小写
- 如果触发器未指定事件类型，则匹配该来源的所有事件

### 通用事件适配器

处理通过通用格式发送的事件，适用于任何自定义的事件来源。

**验证机制**：
- 通用适配器不执行额外的安全验证
- 事件的安全性由 AgentLoom API 的认证机制保障（JWT 或 API Key）

**事件匹配**：
- 根据触发器配置的事件类型与实际事件的类型进行匹配
- 匹配时忽略大小写
- 如果触发器未指定事件类型，则匹配所有通用事件

## 创建 API 事件触发器

### 第一步：进入触发器管理

> 界面提示：在工作流编辑页面中，找到触发器管理区域，点击「创建触发器」按钮。

### 第二步：选择触发器类型

在触发器类型选择中，选择「API 事件触发」。

### 第三步：配置触发参数

填写以下信息：

- **名称**：为触发器设置一个描述性的名称，例如「GitHub Push 事件处理」
- **描述**（可选）：说明触发器的用途
- **事件来源（Event Source）**（必填）：指定监听的事件来源标识，例如 `github` 或 `generic`
- **事件类型（Event Type）**（必填）：指定要匹配的事件类型，例如 `push`、`pull_request`
- **过滤表达式（Filter Expression）**（可选）：进一步过滤事件的条件表达式

### 第四步：确认创建

填写完成后，点击确认按钮即可创建。

## 集成 GitHub Webhook

以下是将 GitHub 仓库的事件接入 AgentLoom 的完整步骤：

### 在 AgentLoom 中准备

1. 为目标工作流创建一个 API 事件触发器
2. 将事件来源设置为 `github`
3. 将事件类型设置为你想监听的 GitHub 事件，例如 `push`
4. 记录下你设置的 Secret（如果需要签名验证）

### 在 GitHub 中配置

1. 进入 GitHub 仓库的 Settings 页面
2. 点击左侧菜单中的 Webhooks
3. 点击 Add webhook
4. 在 Payload URL 中填入 AgentLoom 的 API 事件入口地址
5. 将 Content type 设置为 `application/json`
6. 在 Secret 中填入你在 AgentLoom 触发器中配置的 Secret
7. 选择你想要接收的事件类型
8. 点击 Add webhook 完成配置

### GitHub 支持的常见事件类型

| 事件类型 | 说明 |
|---------|------|
| `push` | 代码推送到仓库 |
| `pull_request` | 拉取请求的创建、更新、合并等 |
| `issues` | Issue 的创建、修改、关闭等 |
| `release` | 新版本发布 |
| `create` | 创建分支或标签 |
| `delete` | 删除分支或标签 |

## 使用通用事件

通用事件适用于自定义的事件来源，你可以从任何系统发送事件到 AgentLoom。

### 发送通用事件

通过调用 AgentLoom 的 API 入口发送事件：

```
POST /api/v1/api-events
```

请求体中需要包含事件的来源、类型和载荷数据。发送请求时需要携带有效的认证信息（JWT Token 或 API Key）。

### 事件匹配规则

通用事件的匹配规则较为简单：

1. 系统检查事件来源是否为 `generic`
2. 如果触发器配置了事件类型，则比较事件的实际类型（不区分大小写）
3. 如果触发器未配置事件类型，则匹配所有通用事件

## 事件处理的时序

API 事件从接收到触发执行的完整时序如下：

1. 外部系统发送事件到 AgentLoom API 入口
2. 系统根据事件来源选择对应的适配器
3. 适配器验证事件的合法性
4. 如果验证失败，拒绝事件并记录历史
5. 如果验证通过，遍历所有已启用的匹配触发器
6. 对于每个匹配的触发器，在租户事务提交后将工作流执行入队
7. 工作流执行异步启动

## 查看事件历史

API 事件触发器的执行历史会记录每次事件到达后的处理结果，包括验证是否通过、是否成功触发了工作流执行等信息。

> 界面提示：在触发器详情页面中，可以查看该触发器的完整执行历史，支持按状态筛选和分页浏览。

## 与 Webhook 触发器的区别

虽然 API 事件触发器和 Webhook 触发器都可以接收外部请求，但它们有以下关键区别：

| 对比项 | Webhook 触发器 | API 事件触发器 |
|--------|--------------|---------------|
| 入口 | 每个触发器有独立的 URL | 共用统一的 API 事件入口 |
| 验证方式 | Token / HMAC 签名 | 事件源适配器 + API 认证 |
| 事件路由 | 一对一（URL 直接对应触发器） | 一对多（事件可匹配多个触发器） |
| 适用场景 | 简单的外部回调 | 复杂的事件驱动架构 |

## 常见问题

### GitHub Webhook 事件没有被触发器匹配

检查以下几点：
1. 触发器的事件来源是否设置为 `github`
2. 事件类型是否正确匹配（注意大小写不影响匹配）
3. GitHub Webhook 的 Secret 配置是否与触发器中的一致
4. 触发器是否处于启用状态

### 签名验证总是失败

确认以下几点：
1. GitHub Webhook 的 Secret 与 AgentLoom 触发器配置的 Secret 完全一致
2. GitHub Webhook 的 Content type 设置为 `application/json`
3. 没有中间代理修改了请求体内容

### 通用事件没有触发工作流

检查以下几点：
1. 请求是否携带了有效的认证信息
2. 事件来源是否与触发器配置一致
3. 事件类型是否匹配（如果触发器指定了事件类型）
4. 工作流是否已发布
